# 05 复盘与下一步

## 最难的问题：保存待确认草稿与确认生效的边界

在离线流程和程序边界测试通过后，首轮真实模型评估仍只有 10/14 个场景满足产品断言。失败包括固定时间冲突、软规则风险、保存时新增占用和更换可用时段。

实际 Trace 表明，模型把“需要用户确认”解释为“不能保存任何草稿”，因此提前 `finish`。例如固定 18:00 被占用，工具已返回 19:00，但模型说无法在此取得确认，便结束；软风险则在规则检查后停止。

这轮没有越权保存，也没有虚报成功，但没有完成本地待确认草稿目标。尤其是 `time-conflict`、`changed-slot` 输出中的 19:00 或 20:00 来自工具首候选，两例模型没有调用保存，不能把它包装成模型已经完成选时。`conflict-on-save` 曾尝试保存 17:00 并遇到冲突，重查得到 19:00 后才提前结束，同样没有保存替代提案。

原始输入、输出、Trace、数据库快照、断言和代码保存在 [v1 归档](../examples/iterations/v1/)。

## 修改与复测

针对提前退出，修改了模型契约中对工具用途的说明：`save_draft` 只持久化本地提案，不确认、不执行发布；固定改期或软风险仍可以保存为 `pending`。提示词与后续验收要求模型显式传入从最新观察中选择的 `suggested_time`；工具 API 仍兼容省略后使用首候选，不能把这一要求写成程序层的必填校验。

工具约束保持不变：固定时间的替代建议仍待确认，软风险仍待确认，硬阻断仍不能保存。评估没有把原来的未完成改算通过，也没有放宽原业务断言；后续额外增加显式选时参数与真实保存时间一致的断言，因此不能声称两轮全部断言完全相同。

修复后全量实际为 14/14 个场景达到预期、176/176 条断言、61 次服务响应；5 个关键场景各重复 3 次，实际为 15/15 次达到预期、210/210 条断言、84 次服务响应。这是有限合成场景的观察，不是通用模型准确率。逐项证据见 [评估文档](03-evaluation.md)。

此外，输出增加由可信状态推导的待确认项，具体列出原时间/建议时间及风险规则证据，便于用户理解要确认什么。

## 学到的内容

- 单元测试能证明约束和持久化，却不能代替真实模型对工具语义的理解验证。
- 幂等既用于普通重复请求，也用于“已写入但响应未知”的恢复；不能把所有异常都称为保存失败。
- 查询时可用不保证保存时可用，冲突检查与写入必须处于同一事务。
- 模型的合理保守也可能导致任务未完成，应同时关注越权和不必要的提前停止。
- 上限终止与草稿状态属于不同维度，必须同时保留事实。
- “当前数据”有明确生命周期：新工具实例读取资料；旧草稿幂等恢复不会自动重新审核。

## 下一步

1. 补充带版本的人工确认、取消和到期释放流程，确认只作用于用户看到的那一版提案。
2. 从合成标签/关键词扩展到真实素材证据读取，保留来源、版本与审核依据。
3. 增加未见场景和更长时间窗口评估，验证结论是否能泛化；当前有限样例不足以证明。
4. 在真实平台接入前，另行设计外部幂等、权限与结果核对，本项目不声称已经完成这些能力。
