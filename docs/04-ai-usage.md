# 04 AI 使用、贡献与验证边界

## 使用范围

本项目允许并实际使用了 AI 辅助。开发协作包括主 Agent、执行 Agent、独立验收 Agent；项目运行时的业务决策模型为 `qwen3.8-max`，二者职责不同。

| 工作 | 实际完成方式 |
|---|---|
| 需求拆分与选题策略 | 用户提供试卷、要求有竞争力；开发主 Agent 提出范围与验证策略 |
| 核心代码 | 执行 Agent 编写模型适配、循环、工具、存储与 CLI；主 Agent 审查业务及接口边界 |
| 验收 | 独立验收 Agent 编写并运行无网络测试，读取实际代码与结果提出缺陷；主 Agent裁定与题面一致的合同 |
| 合成数据与真实评估 | 主 Agent 构造场景，通过真实 CLI 调用用户指定模型，保存实际输出、Trace、数据库快照 |
| 文档 | AI 根据代码、真实测试与服务响应撰写，避免把设计目标写成已验证效果 |
| 模型运行 | `qwen3.8-max` 根据用户请求及逐步工具观察提出 JSON 动作，程序执行和校验 |

## 用户与 AI 的贡献如何区分

用户实际提供了题目、交付目标、质量要求、2–3 小时计划要求、协作分工要求、模型与调用凭据，并要求新建 GitHub 仓库。

当前记录不能证明候选人手工编写或逐行审阅了这些代码，也不能把 AI 的修改归为候选人的个人实现。代码实现、自动测试、运行评估和初稿文档均由本次开发协作完成。候选人的后续人工修改与独立验证，如有发生，应另记具体文件、原因、命令和结果。

## 实际审查和修改

以下修改由开发主 Agent / 验收 Agent 发现并协调执行 Agent 完成，不宣称是候选人的手工修改：

1. 请求绑定从只考虑复合标识，明确为全局 `request_id` 绑定原始载荷，防止换素材绕过。
2. 标题或版权资料缺失返回 `needs_input`，与硬规则阻断区分。
3. 软风险无论是否改期都保留待确认状态；模型不能伪造确认。
4. 排期源快照更新替代仅首次导入，避免改期或删除后留下旧占用。
5. 上限处同时保留“运行未完成”和“草稿实际已保存”，避免误报写入失败。
6. 真实模型初轮将待确认草稿误解为需要先取得同意，提前结束；澄清本地提案保存与确认生效的语义，保留原业务断言，并额外增加模型显式选时参数与落库时间一致的断言后复测。
7. 待确认项由实际选择时间、原请求和规则证据导出，不接受模型自报。

## 凭据与数据

业务资料全部合成。实际 API Key 只在运行进程中注入；仓库只包含环境变量模板。Trace 记录动作、简要依据、工具摘要及服务返回模型/调用标识/用量，不保存 Authorization 头或内部思考内容。

项目未验证真实内容平台、真实版权材料或线上发布效果，也未把测试通过率当成通用模型准确率。

GitHub 仓库由用户创建；代码发布与最终 commit SHA 由交付时的远端记录核验。

## 提交后自审修订

用户要求锐评并执行改进。主 Agent 复现规则缺失放行、SQLite 拒写误标模型失败、损坏库无结构化结果；随后实现修复。验收 Agent 新增21项测试，首次出现的Windows文件清理错误来自测试连接未关闭，修正helper后通过，断言未放宽。实验 Agent 编写偏好对照；协作进程因额度中断，后续全量测试、真实模型运行和最终核验由主 Agent完成，不声称新增独立验收已完成。

当前修改、测试与文档仍为AI协作完成，不能算作候选人的亲手实现。新条件在调试时已经可见，不称隐藏测试。真实偏好实验比较最早候选及已给结构化标签的规则oracle，结论限于已知合成样本，不宣称模型普遍胜过规则。历史证据与源码快照保留，修订复测另存 examples/revision。
